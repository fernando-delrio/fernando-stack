# Clean up AI traces

**What it is for:** making the code look written by a person who knows what they are doing. Every comment that stays has to add something the code does not say. That way it reads fast and nobody dismisses it as "made with AI".

**The golden rule: only comments, docstrings and log messages are touched.** Never code, names or formatting. If something in the code also smells of AI (a strange name, a layer that is not needed), it is noted and proposed separately. When in doubt, the comment stays.

Adapted from antislop-code (github.com/miqdadbadjuber/anti-slop, MIT) and from rule 11 of the `code-style` skill.

## What gets removed

| Trace | Example | Why it is not needed |
|---|---|---|
| Comment that repeats the line | `# Increment the counter` above `counter += 1` | The code already says it |
| Step-by-step narration | `# Step 1: we validate…`, `// Now we fetch…`, `# First, …` | Tutorial tone; if a block needs a title, it is a function |
| Banners and separators | `# ======`, `// ----------`, `# ── Requests ──`, `#####` | Decoration; if the file needs sections, it needs splitting |
| Empty labels | `# Main logic`, `# Imports`, `# Helper functions` | They say nothing |
| Emojis in comments and logs | `# ✅ Done`, `logger.info("🚀 Starting")` | Noise; in a log, they also dirty searches |
| Signatures and attributions | `# Generated by Claude`, `// Created with Copilot`, `Co-Authored-By` in a file | Git says who the author is, not the code |
| Filler notices | `# Note: …`, `# IMPORTANT: …` that warn of nothing specific | If it is important, say what and why without the label |
| Docstrings that repeat the signature | `"""Gets the order by id.\n\nArgs:\n    id: the id"""` on `get_order(id)` | The name and the types already tell it |
| TODO without a task | `# TODO`, `# TODO: improve` | A TODO with no what and no why never gets done |
| Closing markers | `# end if`, `// end function` | The indentation already marks it |
| History and issues | `# Fixed in #123`, `# This used to do X` | That is what git is for |
| Commented-out code | `# old = calculate_v1(x)` | That is what git is for |
| One comment per line | Every line with its own `# …` | One per logical block, at most |

## What always stays

- **The why:** a decision that cannot be deduced from the code. `# Here and not in every service: that way a 401 is handled the same in all of them.`
- **Business logic** that is not obvious: `# The SLA starts at the customer's first message, not when the conversation opens.`
- **Security, concurrency and performance:** `# FOR UPDATE SKIP LOCKED: two workers never take the same job.`
- **API contracts and external protocols:** `# The provider signs with HMAC-SHA256 over the raw body, not over the parsed JSON.`
- **Workarounds and edge cases**, with the cause: `# The Windows console uses cp1252 and breaks when printing emojis.`
- **Legal notices and licenses.**
- **TODOs with a concrete task:** what is missing and why it is not done now.

## Emojis in text the user sees

An emoji inside a chat message, an email or a button **is not an AI trace: it is a product decision.** It is not touched without asking the user. The script flags them separately ("emoji in text") precisely for that.

## How the comment that stays is written

- In the language of the team.
- One line. Two only if the second adds a new fact.
- Short, natural sentences, without "This method…", "What we do here is…" or "It is worth noting that…".
- It goes above the block it explains, not at the end of each line.

## The method

1. **Search with the machine:**
   ```bash
   python -I <path-to-this-skill>/find_ai_traces.py <project-folder>
   python -I <path-to-this-skill>/find_ai_traces.py <project-folder> --docs   # includes .md
   ```
   It lists every suspicious line with its reason: emoji in a comment, emoji in text, banner, AI signature, narration, empty label, filler notice, TODO without a task, closing marker or issue reference. It changes nothing.
2. **Read what the script does not see:** docstrings that repeat the signature, multi-line comments that narrate, commented-out code and comments that no longer match the code. For that you have to read the files, starting with the biggest and most recent.
3. **Decide each warning with the two tables above.** The script errs on purpose on the side of excess: `claude-haiku-4-5` in an environment variable is a model name, not a signature.
4. **Clean file by file.** If a comment explained a whole block, it is not simply deleted: propose extracting that block to a named function (`refactor` skill), as a separate step.
5. **Check that nothing else changed:** tests and lint green. The diff should only have comment lines deleted or rewritten.
6. **Report to the user:** how many comments were removed and how many rewritten, which emojis in user-facing text were left and which code matters were noted for another step. The commits are theirs to make.
