# Limpiar el rastro de IA

**Para qué sirve:** que el código parezca escrito por una persona que sabe lo que hace. Cada comentario que queda tiene que aportar algo que el código no dice. Así Fernando lo lee rápido y nadie lo descarta por «hecho con IA».

**La regla de oro: solo se tocan comentarios, docstrings y mensajes de log.** Nunca código, nombres ni formato. Si algo del código también huele a IA (un nombre raro, una capa que sobra), se apunta y se propone aparte. Ante la duda, el comentario se queda.

Adaptado de antislop-code (github.com/miqdadbadjuber/anti-slop, MIT) y de la regla 11 de la skill `estilo-codigo`.

## Qué se quita

| Rastro | Ejemplo | Por qué sobra |
|---|---|---|
| Comentario que repite la línea | `# Incrementa el contador` sobre `contador += 1` | El código ya lo dice |
| Narración paso a paso | `# Paso 1: validamos…`, `// Now we fetch…`, `# Primero, …` | Tono de tutorial; si un bloque necesita título, es una función |
| Banners y separadores | `# ======`, `// ----------`, `# ── Peticiones ──`, `#####` | Decoración; si el archivo necesita secciones, necesita partirse |
| Etiquetas vacías | `# Main logic`, `# Imports`, `# Funciones auxiliares` | No dicen nada |
| Emojis en comentarios y logs | `# ✅ Listo`, `logger.info("🚀 Arrancando")` | Ruido; en un log, además, ensucian las búsquedas |
| Firmas y atribuciones | `# Generated by Claude`, `// Created with Copilot`, `Co-Authored-By` en un archivo | El autor lo dice git, no el código |
| Avisos de relleno | `# Note: …`, `# IMPORTANT: …` que no avisan de nada concreto | Si es importante, se dice qué y por qué sin la etiqueta |
| Docstrings que repiten la firma | `"""Obtiene el pedido por id.\n\nArgs:\n    id: el id"""` en `obtener_pedido(id)` | El nombre y los tipos ya lo cuentan |
| TODO sin tarea | `# TODO`, `# TODO: mejorar` | Un TODO sin qué y sin por qué no se hace nunca |
| Marcadores de cierre | `# end if`, `// end function` | El sangrado ya lo marca |
| Historial e issues | `# Arreglado en #123`, `# Antes esto hacía X` | Para eso está git |
| Código comentado | `# antiguo = calcular_v1(x)` | Para eso está git |
| Un comentario por línea | Cada línea con su `# …` | Uno por bloque lógico, como mucho |

## Qué se queda siempre

- **El porqué:** una decisión que no se deduce del código. `# Aquí y no en cada servicio: así un 401 se trata igual en todos.`
- **Lógica de negocio** que no es obvia: `# El SLA empieza al primer mensaje del cliente, no al abrir la conversación.`
- **Seguridad, concurrencia y rendimiento:** `# FOR UPDATE SKIP LOCKED: dos workers nunca cogen el mismo job.`
- **Contratos de API y protocolos externos:** `# Chatwoot firma con HMAC-SHA256 sobre el cuerpo crudo, no sobre el JSON parseado.`
- **Workarounds y casos límite**, con la causa: `# La consola de Windows usa cp1252 y rompe al imprimir emojis.`
- **Avisos legales y licencias.**
- **Los TODO con tarea concreta:** qué falta y por qué no se hace ahora.

## Emojis en textos que ve el usuario

Un emoji dentro de un mensaje de WhatsApp, un correo o un botón **no es rastro de IA: es una decisión de producto.** No se toca sin preguntar a Fernando. El script los marca aparte («emoji en texto») justo para eso.

## Cómo se escribe el comentario que queda

- En castellano, salvo que el proyecto entero esté en inglés.
- Una línea. Dos solo si la segunda aporta un hecho nuevo.
- Frases cortas y naturales, sin «Este método…», «Aquí lo que hacemos es…» ni «Cabe destacar que…».
- Va encima del bloque que explica, no al final de cada línea.

## El método

1. **Buscar con la máquina:**
   ```bash
   python -I <ruta-de-esta-skill>/buscar_rastro_ia.py <carpeta-del-proyecto>
   python -I <ruta-de-esta-skill>/buscar_rastro_ia.py <carpeta-del-proyecto> --docs   # incluye .md
   ```
   Lista cada línea sospechosa con su motivo: emoji en comentario, emoji en texto, banner, firma de IA, narración, etiqueta vacía, aviso de relleno, TODO sin tarea, marcador de cierre o referencia a un issue. No cambia nada.
2. **Leer lo que el script no ve:** docstrings que repiten la firma, comentarios de varias líneas que narran, código comentado y comentarios que ya no cuadran con el código. Para eso hay que leer los archivos, empezando por los más grandes y los más recientes.
3. **Decidir cada aviso con las dos tablas de arriba.** El script se equivoca a propósito por exceso: `claude-haiku-4-5` en una variable de entorno es un nombre de modelo, no una firma.
4. **Limpiar archivo a archivo.** Si un comentario explicaba un bloque entero, no se borra sin más: se propone extraer ese bloque a una función con nombre (skill `refactorizar`), en un paso aparte.
5. **Comprobar que no ha cambiado nada más:** pruebas y lint en verde. El diff solo debería tener líneas de comentario borradas o reescritas.
6. **Informar a Fernando:** cuántos comentarios se han quitado y cuántos reescrito, qué emojis de textos de usuario se han dejado y qué cosas de código se han apuntado para otro paso. Los commits los hace él.
